# Design Review для oracul

Используй этот skill, когда пользователь просит улучшить внешний вид, UX, главный экран, форму, кнопки, состояния загрузки/ошибки, мобильную версию или общее ощущение продукта.

## Главный принцип

`oracul` — это не обычный SaaS-интерфейс. Это мягкий арт-оракул: настроение пользователя, картина, спокойный ответ, немного мистики и музейной эстетики.

Не превращай проект в сухой корпоративный лендинг. Улучшай аккуратно: чище, понятнее, красивее, но без потери текущей идеи.

## Перед изменениями

1. Прочитай текущий UI-код, особенно главную страницу, компоненты формы, результата, загрузки и ошибки.
2. Определи, какую пользовательскую проблему решает изменение.
3. Если пользователь просит только анализ — не меняй код, дай короткий список идей.
4. Если пользователь просит реализовать — сделай минимальный focused diff, без большого редизайна всего проекта.

## Чеклист дизайна

Проверь:

1. **Первое впечатление**
   - понятно ли за 3–5 секунд, что делает сайт;
   - виден ли главный сценарий: написать настроение и найти картину;
   - не перегружен ли первый экран.

2. **Визуальная иерархия**
   - есть один главный акцент;
   - CTA-кнопка заметна;
   - второстепенные элементы не спорят с главным действием.

3. **Атмосфера**
   - цвета, шрифты и отступы поддерживают спокойное арт-настроение;
   - дизайн не выглядит случайным набором эффектов;
   - декоративность не мешает чтению.

4. **Состояния интерфейса**
   - пустое состояние понятно;
   - кнопка disabled выглядит осознанно;
   - загрузка спокойная и не пугающая;
   - ошибка объясняет проблему человеческим языком;
   - результат легко прочитать.

5. **Адаптивность**
   - главный сценарий работает на мобильном экране;
   - текст не становится слишком мелким;
   - кнопки и поля удобно нажимать пальцем;
   - важные блоки не прилипают друг к другу.

6. **Доступность**
   - контраст текста достаточный;
   - фокус и keyboard-навигация не сломаны;
   - интерактивные элементы имеют понятные подписи;
   - анимации не мешают использованию.

## Как вносить изменения

1. Используй существующий стиль проекта и текущую систему классов.
2. Не добавляй тяжёлые UI-библиотеки без явной причины и согласования.
3. Не удаляй функции ради красоты.
4. Не меняй бизнес-логику, если задача только про дизайн.
5. Не делай большой редизайн, если можно улучшить точечно.
6. Пиши код так, чтобы его было легко откатить или продолжить.

## Проверка после изменений

Если менялся UI:

1. Запусти lint:

```bash
npm run lint
```

2. Если изменение затрагивает главный сценарий, запусти e2e-проверки:

```bash
npm run test:e2e
```

3. Если есть возможность, открой страницу в браузере и проверь:
   - главный экран;
   - ввод настроения;
   - загрузку;
   - результат;
   - ошибку;
   - мобильную ширину.

## Как объяснять результат пользователю

Пиши простым русским языком:

- что стало понятнее;
- что стало аккуратнее визуально;
- что специально не трогалось;
- какие проверки прошли.

Не перегружай пользователя техническими деталями, если он сам их не попросил.
